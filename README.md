# rmlive

## Joe Says

I have a Remarkable Paper Pro. I love the hardware. I have found no tooling I like for actually projecting the darn thing in a lecture. So I pointed a capable model at the problem.

The main feature is it serves a web service off the Pro that streams frames to a browser tab. So you plug in over USB-C in developer mode, open a browser tab pointed at 10.xxx or whatever, and you get a decent interface:

<img width="1582" height="1035" alt="image" src="https://github.com/user-attachments/assets/698aa6d7-1c0a-4e0f-bbf1-d5f87bcac74a" />

Main things that are better than default is you can *pick the color* for each color to map to (so you aren't projecting colors like `#FF0000`, the default), you get fullscreen, you get good rotation control, and nothing is showing a logo or word mark along with your content.

The other little things are scripts for programmatically copying PDFs to and from the device, which you otherwise have to do through a web interface. But these are just little wrappers around curl.

Claude wrote all the Rust code, the profiling code, responded to profiles that I generated by doing specific actions that seemed laggy, etc. The result is pretty snappy.


## Claude Says

Live view of a reMarkable Paper Pro's screen in a browser, over the USB
cable, with recolorable inks for projecting. One small Rust binary runs on
the tablet; the viewer is a page it serves.

## Usage

Plug in the tablet (developer mode, `remarkable` ssh alias pointing at
`root@10.11.99.1`), then:

```
./run              # build, deploy if changed, (re)start, open http://10.11.99.1:8099/
./run --prof       # same, with profiling logs on
./run stop         # stop it on the tablet
./run status       # running? what does the log say?
./run log          # tablet-side log
./run prof         # pull profiling logs and print a summary
./run bench        # time read/hash/encode on the tablet
./run put a.pdf https://…/b.pdf   # upload PDFs/EPUBs, local files or URLs
./run put --replace https://…/b.pdf   # replace the same-named document instead of adding a copy
./run put --folder Drafts https://…/b.pdf             # into a folder (created if missing; A/B nests)
./run put --replace --folder "CSE 11" https://…/b.pdf # one true copy within that folder
./run ls                          # list documents on the tablet, newest first
./run get week3-friday --last     # download as PDFs with ink, into the current dir
./run get -o ~/Desktop Notebook   # -o picks the directory
./run get --palette projector regions.pdf   # ink remapped to the Projector palette
./run get --palette my.json regions.pdf     # palette = viewer "Copy palette" JSON (file or inline)
```

`./run put` uses the tablet's USB web interface (`POST /upload`, the
same import path as the web page, so documents land in the top level with
proper metadata). The setting can read "on" while the server isn't
actually running; toggling it off and on with the cable plugged in starts
it. `./run put` checks first and says so.

Plain `put` always adds a new document, duplicates included.
`--folder` uploads into a folder: an existing one directly (the upload goes
to the folder last browsed via `GET /documents/<id>`), a missing one by
creating it.
`put --replace` (PDFs only) leaves exactly one document with that name,
looking only inside `--folder` if given (so same-named drafts elsewhere
don't interfere), otherwise anywhere. The web interface can't create
folders, delete, or replace, so those edit xochitl's files over ssh with
xochitl stopped and restart it, once per `put` (6–9 s; the web interface
and the streamer come back on their own):

- old copy has no ink: upload the new one, delete the old, move the new
  one into the old one's folder;
- old copy has ink and the same page count: swap the PDF under it, keeping
  the document, its ink, and inserted pages;
- old copy has ink and a different page count: refuse (ink would land on
  the wrong pages); nothing changes;
- several documents with that name: refuse and list them.

The page count comes from poppler's `pdfinfo` (`brew install poppler`).

`./run get` uses the same interface (`GET /download/<id>/pdf`, what the
web page's download button does): notebooks and marked-up PDFs come back
as vector PDFs with the ink, including inserted pages, in the tablet's stock
ink colors. `--palette` rewrites the ink stroke colors: 'projector' (the
viewer's preset) or a palette from the viewer's Copy palette button (file or
inline JSON) — stock green/blue/yellow/red → your chosen colors; black and
unrecognized pens pass through; the printed page's own colors are untouched. A name matches exactly (case-insensitive, `.pdf` optional) if
anything does, otherwise as a substring, and every match is downloaded;
duplicate names get an ID suffix. Folders are searched too. `--last` is
the most recently modified document. The tablet's clock is off, so the dates
in `./run ls` are good for ordering only.

`./run [--prof] [interval_ms]` passes its arguments to the binary. The
default poll interval is 33 ms. The streamer doesn't survive a tablet
reboot; `./run` again.

### Viewer controls

- **Presets:** Projector (dark, readable inks on white), Dark (light inks on
  dark), Original.
- **Inks:** one color picker per pen color; ↺ resets one. "Detect inks on
  page" adds any other saturated color it finds (it also runs on connect).
- **Background**, **rotate**, **crop** (e.g. Crop L ≈ 110 hides the portrait
  toolbar).
- **F** fullscreen, **H** hide the panel. Panel and cursor hide when the
  mouse is still. Settings persist in the browser's localStorage.
- Bottom-left status shows KB/s and updates/s.

`./run` opens the viewer in a small Mac app (`mac/main.swift`, a window
around a WKWebView, built with `swiftc` into `target/rmlive.app`). `./run
app` opens just the app; `RMLIVE_BROWSER=1 ./run` uses the default browser
instead. The app keeps its own localStorage, so presets saved in a browser
don't carry over. The page reaches native code through
`window.webkit.messageHandlers.rmlive` (fullscreen so far); in a browser
that's absent and it uses web APIs. macOS asks for Local Network permission
on the app's first launch, and again after a rebuild.

## How it works

**Finding the screen.** xochitl (the reMarkable UI) renders the page into a
malloc'd BGRA buffer (byte order B,G,R,A; native-endian ARGB on the
little-endian ARM — an RGBA reading swaps red and blue, leaves
green/black unchanged): 1632-pixel rows (1620 visible + 12 padding), 2160
rows, upright, full color. It sits on a page boundary with a 16-byte glibc
chunk header whose size field is `0xD73000 | flags`. A second, same-sized
allocation holds the gray e-ink buffer (1 level byte + 3 unused per pixel,
17 gray levels, rotated); the alpha byte tells them apart (255 in the color
frame, 0 in the gray one). `find_frames` scans xochitl's rw mappings for
that header and checks alpha. There's no `/dev/fb0` on this device, only
DRM.

**Polling** (`capture_loop`). Every 33 ms: read the frame in 16-row bands
with `process_vm_readv` (2× faster than `/proc/<pid>/mem`) and hash each
64×64 tile's slice of the band while it's in cache. Tiles whose hash changed
are dirty. Comparing against the previous frame instead was
memory-bandwidth-bound and twice as slow. Ticks take ~20 ms.

**Sending** (`stream_to`). Each viewer has a pending set of dirty tiles plus
the newest frame, not a queue. Its connection thread encodes and writes
whenever its previous write finished, so a slow viewer skips intermediate
frames instead of falling behind. Big updates (≥64 tiles) are compressed on
two threads and go out as two messages.

**Wire format.** A long-lived `GET /stream` response carrying messages:
12-byte header (u32 LE payload length, seq, server ms), then raw deflate of
`u16 count` followed by, per tile, `u16 x, y, w, h` and `w*h` RGB bytes.

**Recoloring** (in the page). Pens are stored as pure primaries (`#00ff00`,
`#ffff00`, `#0000ff`, `#000000`). Each pixel is read as
`white + a·(ink − white)`; the page finds the closest ink, keeps `a`, and
substitutes the chosen ink and background, so anti-aliasing survives.
Pixels no ink explains (UI chrome) pass through. Results are memoized per
palette.

## Performance (Oct 2026, firmware 3.23.0.64, profiled)

| | median |
|---|---|
| pen down → change seen by the poller | 45 ms |
| tick (read + hash) | 20.5 ms |
| small update: change seen → written | 22 ms |
| big update (zoom): change seen → written | 87 ms (encode ~39 ms on 2 threads) |
| viewer: inflate + apply + paint | ~6 ms |

Streamer CPU is about half of one of the four cores while a viewer is
connected (it idles when none is).

## Profiling

`./run --prof` makes the tablet write per-tick and per-send JSONL to
`/tmp/rmlive-prof.jsonl`, log pen down/up from `/dev/input/event2`, and
accept viewer timings at `POST /clientstats` (→ `/tmp/rmlive-client.jsonl`).
`./run prof` pulls those into `prof/<timestamp>/` and runs
`tools/analyze_prof.py`. `/tmp` on the tablet is RAM, so don't leave
`--prof` on for days.

## Troubleshooting

- **"No route to host" with the cable in:** macOS Local Network permission
  for your terminal app (System Settings → Privacy & Security → Local
  Network). Also check the tablet is awake.
- **Viewer says disconnected:** `./run status`, then `./run`.
- **"0 color frame(s)" in the log:** a firmware update probably changed the
  buffer's size or layout. The recipe that found it: dump xochitl's large
  anonymous rw mappings via `/proc/<pid>/maps` + `dd` on `/proc/<pid>/mem`,
  then look for 4-byte-per-pixel data with a 1632-pixel stride.

## Layout

- `src/main.rs`: the streamer: frame discovery, polling, HTTP, profiling, bench
- `src/index.html`: the viewer, embedded in the binary via `include_str!`
- `run`: launcher
- `tools/analyze_prof.py`: profile summary
- `tools/rmdocs.py`: `./run put` / `ls` / `get`
- `.cargo/config.toml`: cross-compiles to static `aarch64-unknown-linux-musl`
  with `rust-lld`
